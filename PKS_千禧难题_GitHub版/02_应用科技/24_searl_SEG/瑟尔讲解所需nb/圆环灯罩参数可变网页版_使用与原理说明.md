## 零、这个演示在做什么

原版只有两条 `Input`（第二条 `861` 是个残留输出）。全部内容就是：

> 拿一张**带孔月牙环片**（外圈是正 **n** 边形、内圈是半径 **d** 的圆），
> 平移 **shift**、朝一侧倾 **tilt**，绕 z 轴复制 **m** 份 ⇒ 红色一组；
> 同样一张片朝**另一侧**倾 `−tilt`、再复制 m 份 ⇒ 黄色一组；
> 两组交错 ⇒ 编出一只**灯罩**。

nb 默认 `tilt=1, d=0.77, shift=1.1, n=20, m=24` ⇒ **48 片、960 条四边形**，
从正上方俯视就是一只红黄交错的放射状「花」。

三条容易看漏的几何要点：

1. **两组是镜像关系**，不是各自独立的：`k2` 只是把 `k1` 的倾角取反，
   所以 `tilt=0` 时红黄两组**逐点重合**（画面上只剩黄色，因为黄在后画）。
2. **同一方位角上必有一对红黄片**（两组相位相同，都是 `i·2π/m`）——这就是「编织」的来源。
3. `ViewPoint->{0,0,100}` 配 `ViewAngle->0.01` 是**正上方俯视 + 近正交投影**，
   所以 nb 那一帧看到的其实是一只「从上往下看的扁平花」，而不是 3/4 立体图。

## 一、nb 的定义（逐字复刻，未作任何改动）

```mathematica
Manipulate[Module[{frame, hole, disk, k1, k2},
  frame = Table[{Sin[(i*2*Pi)/n], Cos[(i*2*Pi)/n], 0}, {i, n + 1}];
  hole  = Table[{d*Sin[(i*2*Pi)/n] - 1 + d, d*Cos[(i*2*Pi)/n], 0}, {i, n + 1}];
  disk  = {EdgeForm[Thin], Polygon[Join[frame, hole]]};
  k1 = Table[Rotate[Rotate[Translate[disk, {shift, 0, 0}],  tilt, {1, 0, 0}], i 2Pi/m, {0, 0, 1}], {i, m}];
  k2 = Table[Rotate[Rotate[Translate[disk, {shift, 0, 0}], -tilt, {1, 0, 0}], i 2Pi/m, {0, 0, 1}], {i, m}];
  Graphics3D[{Red, k1, Yellow, k2},
    Boxed -> False, SphericalRegion -> True, ImageSize -> 400,
    ViewPoint -> {0, 0, 100}, ViewAngle -> 0.01]],
 Grid[{{Control@{{tilt, 1}, 0, Pi/2},     Control@{{d, 0.77}, 0.7, 0.99, 0.01}},
       {Control@{{shift, 1.1}, -2, 2},   Control@{{n, 20}, 3, 40, 1}},
       {Control@{{m, 24}, 10, 40, 1}}}],
 TrackedSymbols -> {n, tilt, shift, m, d}]
```

## 二、三个必须在页面上交代清楚的关键决定

### 2.1 `Polygon[Join[frame, hole]]` 的正确读法：这是**月牙**，不是「实心圆盘 + 孔线」

`frame` 是单位圆上的 n 边形，`hole` 是**内切于单位圆左端**（`x = −1`）的半径 d 圆。
`Join[frame, hole]` 把两圈点接成**一条**闭合路径。第一眼会以为「内圈自动挖洞」，
但按 Canvas2D 的 `nonzero` 填充规则——

> **两圈同向 ⇒ 孔的绕数仍是 1 ⇒ 孔被填实。**

而 `frame` 的参数化是 `(sin θ, cos θ)`，`hole` 是 `(d sin θ − 1 + d, d cos θ)`，
两圈**都是顺时针**、方向相同 ⇒ 照抄 `Polygon` 的写法会让 `d` 控件**完全失效**
（画面恒为实心外圈）。这与 demo 的设计意图（`d` 越大孔越大、月牙越薄）直接矛盾。

**正解**：月牙 = `{在 frame 内} ∩ {在 hole 外}`，页面按此实现。

实现方式不是用 `even-odd` 填充 —— 那样每片就只能作为**一个整块**参与绘制，
在纯 Canvas2D 上没法跟别的片做深度排序（远片必须先画）。改用**条带分解**：

设 `A_i = frame` 的顶点、`B_i = hole` 的顶点。注意 `hole` 的参数化正好是
`B_i = d·A_i + C`，其中 `C = (d−1, 0)` —— 这是个**相似变换**（d>0，保序），于是

- 四边形 `Q_i = [A_i, A_{i+1}, B_{i+1}, B_i]` **永不自交**（保序 ⇒ 顶点沿边界单调）；
- n 条 `Q_i` 的并集**恰好**是月牙（面积精确相等，桩测断言 `|Σarea − (s_frame − s_hole)| < 1e-12`）。

于是每片月牙 = **n 条独立四边形** ⇒ 960 片四边形可以逐面参与画家算法排序，
既精确又不需要 even-odd 填充。

> 副作用（也是特性）：关掉「片轮廓」时，画的其实就是这 960 条四边形；
> 打开「片轮廓」则每片额外补一条外圈折线 + 一条内孔折线（共 `4m` 条），
> 对应 `EdgeForm[Thin]`。

### 2.2 画家算法：为什么整个场景要**逐面**排序

纯 Canvas2D 没有 z-buffer。页面的做法是把 960 条四边形 + 96 条轮廓线全部扔进一个
列表，按**视空间深度**从远到近排序后依次 `fill()`（`mini3d.js` 的 `List.flush`）。
因为 §2.1 已经把每片拆成不自交的小四边形，**任意两片之间不会出现交叉穿透**，
排序结果就是正确遮挡。

### 2.3 ⚠ `n` 不是 4 的倍数时，孔会从左边探出外圈

`frame` 是**内接**于单位圆的正 n 边形，只在 `270°` 是采样角（即 **n 为 4 的倍数**）时，
它才在 `(−1, 0)` 方向有一个顶点。否则内接多边形在该处向内缩，
而半径 `d`、圆心 `(d−1,0)` 的孔会在那里**探出外圈之外**一段。

- 这是**几何必然，不是 bug**（nb 里同样如此，只是 Mathematica 的 `Polygon` 会把它一起画出来）。
- 页面**主动探测并提示**：`holeOutsideCount(n, d)` 统计有几个孔顶点落在外圈之外，
  > 0 时在「场景账本」下面标一行黄色警告，并提示「把 n 取 4 的倍数即可消掉」。
- 实测：`n=20 ⇒ 0`、`n=8 ⇒ 0`、`n=7 ⇒ 2`、`n=3 ⇒ 2`。
- n=3 时尤其明显（三角形内缩最多），页面默认的实拍图 `网页实拍_整页_n7孔探出提示.png`
  就是专门拍这个提示的。

## 四、GIF 为什么扫 **tilt**，而不是扫相机

**场景本身高度对称**：m 片等角排列 ⇒ 绕 z 轴每转 `360/m` 度就与自身重合
（默认 m=24 时只有 **15°**）。于是：

- 相机公转的 GIF 要么**几乎静止**（转一点就重合了），
  要么转满 360° 后必然出现 **m 段完全重复**的帧 —— 两头都不划算。
- 改为扫描 `tilt`（0 → π/2）：**帧帧都是新画面**，而且正好就是这个演示的主题
  「倾角怎么把月牙片编成灯罩」。

参数：`GIFW = GIGH = 880`、`GIFF = 30` 帧、帧间延迟 7cs。
单张体积实测 1.6–4.4 MB（最重的 `d=0.99, m=40` 为 4.23 MB，仍 < 5 MB）。

> 播放条上的「▶ 播放旋转」是相机公转，和 GIF 的 tilt 扫描是**两件不同的事**，
> 页面上分别标注了，别混。

### 5.1 独立复核 GIF 用的是一个**自己写的 GIF 解码器**

`_rl_web_dev\check_gif.py` 不依赖 PIL、也**不复用**页面的 `gifcodec.js`：
自己解析 GIF89a 块结构（图像描述符 / GCE / NETSCAPE2.0）、自己实现变长 LZW 解码，
把每帧解成索引矩阵后逐帧 md5。九张全过，并且逐帧的「非背景像素占比」
从首帧到末帧**单调上升**（例：`shift=0` 那组 13.5% → 54.2%），
与「tilt 增大 ⇒ 月牙从重合状态散开」的几何预期一致。

### 5.2 踩过的坑（已修，并写了防回归断言）

- **导出文件名必须对「所有会变的量」单射**。第一版文件名叫 `圆环灯罩_d…_n…_m…`，
  没带 `shift` 和配色 ⇒ `shift=0` 与 `shift=1.1 + 彩虹配色` 两个 case **同名**，
  9 个 GIF 静默变成 8 个（后者覆盖前者）。已把 `shift`/配色写进文件名，
  并在桩测加了断言「7 组不同参数 ⇒ 7 个互不相同的文件名」把这条钉死。
