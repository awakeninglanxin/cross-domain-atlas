## 零、这个演示在做什么

把多边形的**每一条边都当成一面镜子**，把整个多边形照过去；照出来的新图形，它的每条边又都是镜子，再照一遍 —— 如此反复。

迭代 `o` 层之后，铺出来的是一个近乎分形的对称网格。`o` 每加 1，线条数量就乘以 `2n`。默认参数（`n=5, α=1.385, o=2`）就已经是 111 条折线；推到 `n=12, o=3` 是 **14 425 条**。

这就是 nb 标题里「超美」的来源。

## 一、nb 的四段定义（逐字复刻，未作任何改动）

```mathematica
reflectLine[Line[l_], Line[{p1_, p2_}]] := Block[
  {dir = #/Norm[#] & [p2 - p1], nor},
  nor = Reverse[dir] {-1, 1};
  Line[Map[(p1 + (# - p1) - 2 (# - p1).nor nor) &, l]]
];

initialSquenchednGon[n_, α_] :=
  Line[Table[If[EvenQ[k], 1, α] {Cos[k Pi/n], Sin[k Pi/n]}, {k, 0, 2n}]] // N;

reflectAll[Line[l_]] := reflectLine[Line[l], Line[#]] & /@ Partition[l, 2, 1];

iteratedReflectedGraphics[o_, n_, α_, pl_] := Module[{aux, prs},
  aux = Reverse@MapIndexed[
      {Hue[0.8 (#2[[1]] - 1)/Max[o, 1]],
       ControlActive[Opacity[1], Opacity[.5]],
       Thickness[(o + 2 - #2[[1]]) 0.005],
       #1} &,
      NestList[Flatten[reflectAll /@ #] &, {initialSquenchednGon[n, α]}, o]
    ] /. Line -> pl;
  prs = Max[Abs[#]] & /@ Transpose[Level[Cases[aux, _pl, ∞], {-2}]];
  Graphics[aux, ImageSize -> {500, 400},
    PlotRange -> {prs[[1]] {-1, 1}, prs[[2]] {-1, 1}},
    ImagePadding -> {{20, 20}, {20, 20}}]
];

Manipulate[iteratedReflectedGraphics[o, n, α, pl],
  {{pl, Line, ""}, {Line -> "line", Polygon -> "polygon"}},
  {{o, 2, "o"}, 0, 3, 1},
  {{n, 5, "n"}, 2, 12, 1},
  {{α, 1.385, "α"}, -2, 2},
  SaveDefinitions -> True, TrackedSymbols :> {pl, o, n, α},
  ContinuousAction -> False]
```

网页里的数学核逐字对应这四段；`Manipulate` 的参数范围、步长、默认值也照抄。

## 二、四个必须先讲清的技术点

### 2.1 `initialSquenchednGon` 其实给了 `2n+1` 个点

```mathematica
Table[If[EvenQ[k], 1, α] {Cos[k Pi/n], Sin[k Pi/n]}, {k, 0, 2n}]
```

`k` 从 `0` 到 `2n`，共 **`2n+1`** 个点；角度 `kπ/n` 以 `2π` 为周期，所以第 `2n` 个点（角度 `2π`）与第 `0` 个点（角度 `0`）**坐标重合** —— 折线天然首尾闭合。

- 偶数 `k` ⇒ 半径 1；奇数 `k` ⇒ 半径 α
- `α = 1` ⇒ 正 `2n` 边形；`α = 0` ⇒ 退化成 `n` 条过原点的辐条；`α < 0` ⇒ 锯齿反向

### 2.2 每个相邻点对都是一面镜子 ⇒ 一次得 `2n` 条新折线

```mathematica
reflectAll[Line[l_]] := reflectLine[Line[l], Line[#]] & /@ Partition[l, 2, 1]
```

`Partition[l, 2, 1]` 是**滑动窗口**（偏移 1），`2n+1` 个点给出 **`2n`** 条相邻边。每条边都当作反射轴，把**整条折线**照一次 ⇒ 一条进、`2n` 条出。

所以：

| 量 | 公式 | `n=5, o=2` | `n=12, o=3` |
|---|---|---|---|
| 第 `g` 代条数 | `(2n)^g` | `1 / 10 / 100` | `1 / 24 / 576 / 13824` |
| 累计条数 | `Σ_{g=0..o} (2n)^g` | **111** | **14 425** |
| 累计点数 | 累计条数 × `(2n+1)` | **1 221** | **360 625** |

`n=12, o=3` 的 14 425 条 × 25 点 = **36 万个点**，这就是为什么页面的建模必须做矩阵化（见 2.3）。

### 2.3 矩阵化：把「逐点反射」压成「一次仿射乘」

朴素做法（照抄 nb）是：对第 `g−1` 代的每一条折线、每一个点、每一次反射，都套一遍 `p1 + (p−p1) − 2((p−p1)·nor) nor`。`o=3` 时这是一条 **嵌套 4 层** 的循环，代价爆炸。

关键观察：**`reflectLine` 是一个仿射变换**。

关于过 `p1`、方向单位向量 `dir` 的直线镜像，法向 `nor = (−dir_y, dir_x)`，可以写成

```
x ↦ A·x + b,   A = I − 2·nor·norᵀ,   b = 2·(p1·nor)·nor
```

`A` 是 2×2 **对称正交**矩阵（`Aᵀ = A`、`A² = I`），`det A = −1` —— 镜像的全部几何性质都在这里面。

于是第 `(i₁ i₂ … i_g)` 条折线就是若干镜像的复合。**递推方向必须写对**：

设 `L = R_i(P)` 是把初始多边形 `P` 关于第 `i` 条边反射的结果。
`L` 的第 `j` 条边被 `R_i` 搬到了新位置 `A = R_i(边 j)`。
关于轴 `A` 的反射 = 共轭 `R_i ∘ R_j ∘ R_i⁻¹`，作用在 `L` 上：

```
(R_i R_j R_i⁻¹) · R_i(P) = R_i R_j (P)
```

⇒ **`T^(g) = T^(g−1) · R_j`（右乘）**，不是左乘。写成 `compose(R, T)` 会让 `o ≥ 2` 全错 —— 这个坑我实际踩过，被 Python 逐点反射法的对拍抓出来了。

矩阵化后复杂度从「每条线 × 每个点 × 逐次反射」降到「每条线 × 一次仿射乘」：

| 算例 | 条数 | 点数 | 网页建模耗时 |
|---|---|---|---|
| `n=5, α=1.385, o=3` | 1 111 | 12 221 | 0.2 ms |
| `n=12, α=2, o=2` | 601 | 15 025 | 0.2 ms |
| `n=8, α=−0.4, o=3` | 4 369 | 74 273 | 0.7 ms |
| `n=12, α=1, o=3` | 14 425 | 360 625 | 12.4 ms |

### 2.4 `PlotRange` 是**逐轴独立**的 —— 所以画面不是等比的

```mathematica
prs = Max[Abs[#]] & /@ Transpose[Level[Cases[aux, _pl, ∞], {-2}]];
PlotRange -> {prs[[1]] {-1, 1}, prs[[2]] {-1, 1}}
```

`prs[[1]]` 是全部点的 **max|x|**，`prs[[2]]` 是 **max|y|**，两者各管一个轴。

配合 `ImageSize -> {500, 400}` 与 `ImagePadding -> {{20,20},{20,20}}`，可用区是 `460 × 360`，于是

```
水平 px/单位 = 460 / (2·max|x|)
垂直 px/单位 = 360 / (2·max|y|)
```

两轴**必然不等比**。默认参数实算：

| 量 | 值 |
|---|---|
| `max|x|` | `5.284759877` |
| `max|y|` | `5.067913897` |
| 水平 px/单位（500 宽下） | `43.52` |
| 垂直 px/单位（400 高下） | `35.52` |
| 比值 | `1.2253` |

网页照抄这套语义：`mkMap(W, H, mx, my)` 里 `px = 20/500·W`、`py = 20/400·H`，`sx = (W − 2px)/(2mx)`、`sy = (H − 2py)/(2my)`，y 轴翻转。这也是为什么主图看着比正方形「扁一点」—— 原版就是这样。

### 2.5 图层顺序：祖先在最上层

`MapIndexed` 给第 `k` 代（`k` 从 1 数起）配：

| 属性 | 公式 | `o=2` 时 |
|---|---|---|
| 颜色 | `Hue[0.8(k−1)/Max[o,1]]` | 第 0 代 `Hue[0]` 红 · 第 1 代 `Hue[0.4]` 绿 · 第 2 代 `Hue[0.8]` 紫 |
| 粗细 | `Thickness[(o+2−k)·0.005]` | `0.015 / 0.010 / 0.005` |
| 不透明度 | `ControlActive[Opacity[1], Opacity[.5]]` | 静止 `0.5`，拖动控件时 `1` |

`Thickness` 在 Mathematica 里是**相对图像宽度**的比例 ⇒ 网页取 `lw = thickness × 画布宽`，与原版一致。

外层的 `Reverse@` 把整个列表倒过来 ⇒ 渲染时**第 `o` 代（后代）先画在底下，第 0 代（祖先）最后画、压在最上面**。网页的 `paintAll` 也是 `for (gi = o; gi >= 0; gi--)`。实拍可以明显看到红色五角星（第 0 代）盖在绿色、紫色之上。

## 四、两种动画 → 一条 τ 进度条

nb 原版是**静态**的（`ContinuousAction -> False`，松手才出图）。网页在不动数学的前提下加了两条动画，共用一根 τ 进度条：

### 逐代渐显（`mode = 'gen'`）

```
第 g 代的不透明度 alpha_g = clamp(τ·(o+1) − g, 0, 1)
```

- `τ = 1` ⇒ 所有 `alpha_g = 1`，画面**与 nb 静止输出一致**（这是验收基准）
- `τ` 从 0 涨到 1 的过程，就是「一层一层往外照」的生成过程

### α 扫描（`mode = 'alpha'`）

```
α = −2 + 4·(1 − |2τ − 1|)
```

三角波：`τ: 0 → ½ → 1` 对应 `α: −2 → +2 → −2`，看去程又看回程。

**⚠ 这个模式曾经有个真 bug**：一开始它只切了 UI（把 α 滑条禁用），几何仍用滑条上的基准 α。修法是把「实际驱动几何的 α」抽成一个函数：

```js
function effAlpha() {
  return (S.mode === 'alpha') ? alphaFromTau(S.tau) : S.alpha;
}
```

`ensureModel` / `buildLayers` / 读数 / 徽标 / GIF 抓帧全部改走 `effAlpha()`；`setMode` 不再动 `S.alpha`；`applyTau` 在 α 模式把扫描值实时写回 α 滑条，让 α 在动这件事**看得见**。

实拍验证（`τ` 扫 5 个点）：

```
α   = [−1.84, 0, +2, 0, −1.84]          ← 三角波，与公式逐位吻合
mx  = [3.3203, 1, 5.3188, 1, 3.3203]    ← 视窗随 α 真实变化
几何矩阵差 Σ|Δ| = 20.64                   ← 几何确实在跟着 τ 走，不只是 UI
α 数字框 = −1.840 ; 半程 +2.000           ← 滑条实时跟随
```

（`α = 0` 时 `mx = 1` 是**正确**的：这时初始点全在单位圆与原点之间，所有镜面都过原点，反射保半径 ⇒ 图形必落在单位圆内。）

### 离屏层缓存

`LY.el[gi]` 为每一代各存一张离屏画布（只烘一层，只含 opacity）。τ 动画每帧只做画布合成 ⇒ 一层都不重画，`n=12,o=3` 也能拖得动。缓存 key 是 `[W,H,n,effAlpha(),o,pl,opacity,lwScale]`，任一变化即整体失效。

## 五、🎞 导出

### PNG

主图直接 `toDataURL` 存盘。

### GIF（复用同一套手写编码器）

不引任何外部库，纯 JS 手写 GIF89a：

- 6 bit 直方图 + **中位切分**量化到 256 色
- 惰性最近色缓存，避免逐像素全表搜索
- LZW 编码的**码长切换时机**与 gif.js 对齐（9 → 12）
- 255 字节子块、`NETSCAPE2.0` 无限循环扩展块

导出长边 900 px，5 档参数（画幅 × 帧数）逐档收敛到 **< 5 MB**。

**★ 归档接口的坑**：CDP 一次性回传几 MB 的 base64 会把连接卡住，所以页面提供 `gifPrepOne / gifChunk / gifClear` 三个函数，由 Node 侧按 400 KB 分片拉取。这一版踩的两个坑都留了断言：

1. `gifPrepOne` 返回结构里**必须有 `b64len`**。原先只返回 `bytes`，归档脚本按 `undefined` 分片 ⇒ 一片都拉不到 ⇒ **静默写出 0 字节文件**。
2. 归档脚本现在对 `b64len` 缺失**直接抛错**，不再写空文件。

## 六、与原版的差异（诚实清单）

**完全照抄的**：四段定义的数学、`ImageSize{500,400}`、`ImagePadding{{20,20},{20,20}}`、分轴独立 `PlotRange`、`Hue[0.8(k−1)/Max[o,1]]`、`Thickness[(o+2−k)·0.005]`、`Reverse@MapIndexed` 的图层顺序、`α=1.385` 等全部默认值与范围步长、`Line`/`Polygon` 二选一。

**有意不同的**：

| 项 | nb 原版 | 网页 | 原因 |
|---|---|---|---|
| 拖动滑条时的刷新 | `ContinuousAction -> False`，松手才出图 | 拖动即实时刷新 | 现代浏览器扛得住；这是体验改进，不改数学 |
| 拖动时的不透明度 | `ControlActive` 自动在 `1` 与 `.5` 之间切 | 单一的「不透明度」滑条，默认 `0.5`（= 原版静止值） | 主动省略了自动切换逻辑，改为手动可控 |
| 静态 → 动态 | 只有静止图 | 两条 τ 动画 + GIF 导出 | 纯增量，`τ=1` 即为原版静止输出 |
| 逐代分解视窗 | 无 | 4 张小画布 | 纯增量，帮助看清生成过程 |
| 图层开关 | 无 | 各代独立开关 | 纯增量 |
| 线宽倍率 | 无 | 整体倍率 | 纯增量，默认 1.0 等于原版 |

**已知限制**：

- 逐代分解格在某代超过 900 条时会抽样绘制（主图不受影响）
- `α` 扫描模式下 `n ≥ 10 且 o=3` 时每帧要重建 1.4 万条线，动画会明显变慢（页面有提示）
- 没有做 WebGL / Worker 加速，`o=3, n=12` 的 36 万点仍在主线程算（12.4 ms/次，可接受）

## 九、一句话总结
