## 二、根因：LZW 扩位时机比规范早一个码

GIF 的 LZW 有一对**必须错开一格**的规则。字典条目满 `2^n` 时：

| 角色 | 规范写法 | 为什么 |
|---|---|---|
| 编码器 | `next > 2^size` 才扩位 | 它已经知道刚分配的那个条目 |
| 解码器 | `next >= 2^size` 就扩位 | 它要等下一个码才知道上一对，永远慢一个条目 |

两者差的这一格，正好等于「字典滞后一格」。**不需要任何手工补偿。**

本页原来写的是：

```js
/* 编码器 */
if (next > (1 << size) - 1 && size < 12) size++;     // 即 next >= 2^size —— 早了一格
/* 解码器 */
if (next + 1 > (1 << size) - 1 && size < 12) size++; // 又手工 +1 补回去
```

编码器提前扩、解码器提前扩，**两边同时错，误差互相抵消**，所以：

- 页内自检（编 → 解 → 逐点比）**77/77 全绿**
- 真实解码器（ffmpeg / Chrome / 任何看图软件）**从第 512 个码起整条位流错位**

改法：

```js
if (next >  (1 << size) && size < 12) size++;   // 编码器：晚一格
if (next >= (1 << size) && size < 12) size++;   // 解码器：不加 +1
```

## 三、怎么把它钉死的（判据本身就是重点）

第一版差点又栽在假绿上：我想拿 `Downloads` 里另外两个 gif 当「已知良好样本」，
但 `分形环套环_….gif` / `合成_….gif` **也是这套自研编码器生成的** —— 拿它当裁判等于自己证明自己。

真正有效的三步：

### ① 找外部裁判

本机有 ffmpeg。`ffmpeg -f lavfi -i testsrc2 ... _gif_ref.gif` 生成一个**标准** gif。

### ② 用标准 gif 反向标定解码规则

| 样本 | `gt`（next > 2ⁿ） | `ge`（next ≥ 2ⁿ） | `ge-1`（next ≥ 2ⁿ−1） |
|---|---|---|---|
| **ffmpeg 生成（权威）** | 7,425 / 30,000 ✗ | **30,000 / 30,000 ✓** | 8,667 / 30,000 ✗ |
| **本页导出（坏）** | 6,680 ✗ | 3,101 ✗ | **90,000 / 90,000 ✓** |

结论一目了然：**规范是解码器 `ge`**，而本页的文件只有 `ge-1` 解得开 ⇒ 编码器早了一格。

### ③ 变异测试：证明探针自己抓得住

新探针 `_probe_gif.cjs` 的 B 段故意把规则改回错的，然后要求 ffmpeg **必须报错**：

```
✓ B1 变异成功注入（旧 bug 写法复活）        [替换 1 处]
✓ B2 变异版本被 ffmpeg 判为坏文件           [LZW decode failed]
✓ B3 变异版本的内容大面积错                 [不一致 2,383,416 / 2,520,000 = 94.6%]
```

没有 B 段，A/C/D 段全绿也不能说明探针有牙。

## 五、给这类 bug 留的三条规矩

1. **自检的解码器必须独立于编码器**。同一份代码的思路写两遍，只能证明「自己和自己一致」。
   现在 `_probe_gif.cjs` 的 C 段固定用 **ffmpeg** 当裁判，4 例 × 252 万像素全量比对。
2. **「长度对」不等于「内容对」**。坏 LZW 不会解不出来 —— 它解出一堆垃圾然后把画布填满
   （实测变异版本反而解出了 252 万像素）。判据必须是**逐像素内容**，不是像素数。
3. **判据放在会出问题那一档**。D 段解析 GCE 时我把 delay 读成了 `0x0E04 = 3588`，
   而判据只写了 `d > 0` ⇒ 3588 也判过。**换成「1..1000 且两帧相等」才抓出来。**
